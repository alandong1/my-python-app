# Dev Lab · 平台需求与设计决定

记录「做什么」和「为什么这样做」。需求有变化时**先改需求文档，再改代码**（见 `AGENTS.md`）。
这里记录**平台层面**的需求；每个项目自己的需求在 `projects/<slug>/REQUIREMENTS.md`。

- 状态标记：✅ 已实现　🔒 已实现但未启用　🚧 进行中　📋 待办　❌ 已放弃
- 每条设计决定都写明原因，方便以后判断还要不要坚持。

## 1. 平台定位

- ✅ **Dev Lab** 是负责人的个人项目平台：以后的游戏、工具、AI agent 等项目都在这里开发和测试。
- ✅ **一个仓库、一个网站、一个数据库、一套开发流程**（`AGENTS.md`）。
  - 原因：负责人希望所有项目共用同一套流程和基础设施，不必每个项目重新搭部署、数据库和登录。
- ✅ 首页 `/` 是「**应用商店**」：卡片列出所有项目（图标、名字、分类、状态、简介），点击进入。
- ✅ 每个项目挂在 **`/apps/<slug>/`** 下。
  - 原因：路径规律统一，不会和平台自己的 `/api`、`/static` 冲突。
- ✅ **未登录也能浏览商店**；进入需要登录的项目时再弹出登录（含游客一键进入），登录后自动进入项目。
- ✅ 项目之间相互隔离：网址、数据库表名（`<slug>_` 前缀）、代码都分开，规则见 `AGENTS.md`「项目之间的边界」。
- ✅ 太重的项目可以单独部署，在商店里用 `external_url` 登记。
  - 原因：所有项目在同一个进程里运行，Render 免费版内存有限；一个项目太耗资源会拖垮整个网站。
- ✅ **中英文切换**：每个页面右上角都有「EN / 中文」按钮，全站（首页、登录、我的账号、各项目页面）同时切换。
  - 默认中文（负责人和主要用户是中文用户）；选择保存在浏览器 localStorage 里（键 `lang`），下次打开保持不变。
  - 做法：共用脚本 `static/i18n.js`。页面上的中文原文就是「键」，英文译文放在字典里，找不到译文就显示中文，所以新增文字时漏翻译不会出现空白。
  - 项目自己的文字翻译放在项目目录里（如 `projects/lordwar/static/lang.js`），用 `i18n.add()` 注册，平台不替项目翻译。
  - 商店里的项目名和简介由 `Project` 的 `name_en`、`description_en` 提供（API 返回 `nameEn`、`descriptionEn`）。
  - 限制：服务器返回的**动态文字**（项目里的战报、部分报错）目前仍是中文，见「待办」。
- ✅ **我的账号**和登录里的报错信息（如「用户名或密码错误」）在字典里有英文译文，英文模式下显示英文。
- ✅ **技术选型按项目需求决定**（2026-11-23）：默认「原生 JavaScript 前端 + Python/FastAPI 后端 + 平台数据库」，放在平台内。需求超出默认技术栈时（例如 3D 游戏、上架应用商店的手机 App、超高并发服务器），由 AI 提出方案和理由，负责人同意后才用，并单独部署、在商店里用 `external_url` 登记。选型标准和对照表见 `AGENTS.md`「技术选型」。
  - 原因：不同项目适合的技术不同；但每多一种语言或服务都会增加部署、维护和费用，所以默认留在平台里，例外要有理由。

## 3. 账户与登录

- ✅ **游客登录**：浏览器第一次访问时在 localStorage 里生成一串随机凭证，作为游客身份。同一个浏览器再来还是同一个人。
  - 限制：换浏览器、换设备、清除浏览器数据后无法找回。登录页面上有提示。
- ✅ **用户名 + 密码**注册和登录。用户名 3–20 个字符（可以用中文，不区分大小写），密码至少 8 位。
- ✅ **可选绑定邮箱**：需要点击验证邮件里的链接才算绑定成功。绑定后也可以用邮箱登录。
  - 🔒 发邮件需要配置 SMTP。没有配置时，验证链接打印在服务器日志里。
- 🔒 **第三方登录：Google、Apple、微信**。代码已完成，并用模拟数据测试过；**配置了对应的密钥才会启用**，目前三个都没有配置。
  - Google：免费，可以随时申请。
  - Apple：需要 Apple Developer Program（每年 99 美元）。
  - 微信：需要企业认证的微信开放平台账号，个人开发者基本无法申请。
  - 已登录的用户（包括游客）可以在「我的账号」里绑定第三方账号；游客绑定后变成正式账号。
- ✅ **账号全平台通用**：在 Dev Lab 登录一次，所有项目都认得同一个人。登录页面在首页，项目页面没登录时跳到首页登录，登录后再跳回来。

**安全方面的决定**
- 密码用 bcrypt 哈希存储；登录会话放在 **HttpOnly cookie** 里，数据库只存会话 token 的哈希。
  - 原因：数据库泄露或网页被注入恶意脚本时，都拿不到能直接登录的凭证。
- 登录、注册有频率限制；WebSocket 拒绝来自其他网站的连接；OAuth 使用 state 参数防止伪造登录。


## 4. 环境与部署

- ✅ **远程测试环境**：Render（网址见 `deploy.conf`）+ Neon PostgreSQL（us-east-2）。目前没有真实用户。
- ✅ 开发流程：本地测试 → push 到**自己的分支** → 开 **PR** → 合并进 `main` → Render 自动部署 → 通知负责人刷新。（2026-11-23 起，之前是直接 push 到 `main`）
  - 原因：开始有其他开发者（人或 AI）参与的可能，需要一道关卡防止未经审核的代码上线。`main` 上的每个提交都会自动部署。
- ✅ AI 助手改动完成、测试通过后**直接开 PR，不用询问负责人**（2026-11-23）。
  - 原因：AI 工具默认「用户没要求就不开 PR」，每次都问很打断。负责人本人的 PR 会自动审核合并，开 PR 本身没有风险；想先看一眼时让 AI 开草稿 PR。
- ✅ **PR 审核规则**（`.github/workflows/pr-gate.yml`）：
  - PR 作者是**负责人本人**（包括负责人指挥的 AI 用负责人的 GitHub 账号开的 PR）→ 自动 approve，测试通过后自动合并。
  - **其他人**开的 PR，不管是手写还是用 AI 写的 → 必须由负责人人工审核 approve。
  - 判断依据是 GitHub 记录的 PR 作者，不能伪造；规则文件运行的是 `main` 上的版本，别人在 PR 里改不掉。
  - 合并用 merge commit（不 squash），分支上的提交原样进入 `main`。
- ✅ **一个 PR 只改一个范围**（2026-11-23）：要么只改一个项目（`projects/<slug>/`），要么只改平台；CI 的 `scope` 检查强制执行。新建项目只需要建自己的目录，平台自动发现。
  - 原因：多个 agent 并行开发多个项目时互不冲突；每个 PR 的影响范围清楚，容易审核和回退。
- ✅ **按改动选测试**（2026-11-23）：只改了一个项目 → 平台测试 + 这个项目的测试；改了平台代码 → 全部测试。本地和 CI 用同一个脚本 `scripts/changes.py`。
  - 原因：项目多了以后，每次跑所有项目的测试既慢又没必要；但平台测试必须跑，因为所有项目在同一个进程里，一个项目坏了会让整个网站起不来。
- ❌ **放弃：「合并前分支必须是最新」和自动同步 PR**（2026-11-23 加上，当天放弃）。
  - 曾经的做法：分支保护要求 PR 合并前必须包含最新的 `main`，`sync-prs.yml` 定时把 `main` 合并进落后的 PR、重跑测试。
  - 放弃原因：多个 agent 并行时，每合并一个 PR 其他 PR 都要排队重新同步；GitHub 的定时任务长时间不触发，PR 一卡就是十几分钟以上；机器人推送的提交还会触发「需要维护者批准」等连锁问题。而它防的「语义冲突」（两个 PR 各自通过、合在一起出错），在「一个 PR 只改一个范围」之后风险已经很低，CI 测试的也是「PR + 开测时最新的 main」。
  - 现在：PR 测试通过就直接合并，不要求是最新；真正有冲突时 GitHub 会拦住，由 PR 的作者合并 `main` 解决。
- ✅ **完成后给出可点击的链接**（2026-11-23）：agent 上线后的最后一条回复必须列出项目页面、PR 等完整链接；`wait_for_deploy.sh` 上线后自动打印这些链接。
  - 原因：负责人同时开多个 agent，每个做完都能直接点开看结果，不用自己拼网址、翻 PR 列表。
- ✅ **自动修复次数上限**（2026-11-23）：同一个 PR 的 CI 失败满 3 次，自动打 `needs-human` 标签、关闭自动合并、通知负责人；AI 看到标签必须停手。负责人去掉标签后计数清零。
  - 原因：AI agent 订阅了自己的 PR，CI 失败会唤醒它去修；如果一直修不好，会无限循环消耗 token。规则写在 `AGENTS.md`，并由 `ci-failure-limit.yml` 强制执行，不只依赖 AI 自觉。
- ✅ **自动测试（CI）**（`.github/workflows/ci.yml`）：每个 PR 在 Python 3.9（本地版本）和 3.12（Render 版本）上跑全部测试，通过才能合并。
- ✅ `main` 有分支保护：禁止直接 push，必须通过 PR，且需要 1 个 approve + 测试通过。
- ✅ **GitHub 仓库公开**（2026-11-23）。
  - 原因：免费账号下，私有仓库不能用 Auto-merge 和分支保护，而 PR 审核规则依赖这两个功能。公开前检查过全部提交历史，没有密钥。
  - 影响：任何人都能看到代码和文档，所以**密钥绝不能进仓库**；任何人都能 fork 后提 PR，由上面的审核规则把关。
  - 只有对仓库有写权限的人（负责人和被邀请的协作者，见 GitHub Settings → Collaborators）的 approve 才算数。目前只有负责人。以后邀请协作者、又希望只有负责人能审核时，加 `CODEOWNERS` 并开启「Require review from Code Owners」（需要同时调整自动 approve 的做法）。
- ✅ 账户和登录会话保存在数据库里。
- ✅ Render 上没有配置 `DATABASE_URL` 时，服务**拒绝启动**。
  - 原因：曾经因为漏配这个变量，服务悄悄用了临时 SQLite 文件，重启后账号全部丢失（2026-11-22）。
- ✅ 开发规范写在 `AGENTS.md`，Claude Code、Codex、Copilot 等 AI 工具共用同一份。

- ✅ 通用的**快照存档服务**（表 `world_snapshots`，按项目 slug 区分），项目可以直接用来保存自己的状态。

## 5. 待办与想法

按大致优先级排列，负责人可以随时调整。

- 📋 **页面自动更新**：发现服务器版本变了，自动刷新或提示刷新。
- 📋 **服务器文字的英文版**：项目服务器生成的文字（如领主战争的战报、带数字的报错）目前只有中文。要翻译需要让服务器返回「消息代号 + 参数」，由前端按语言拼出句子。
- 📋 **配置 Google 登录**：需要负责人先在 Google Cloud Console 申请 OAuth Client。
- 📋 **找回密码**：通过已绑定的邮箱重置密码（需要先配置 SMTP）。
- 📋 **游客升级为正式账号**：游客直接设置用户名和密码（目前只能通过绑定第三方账号升级）。
- 📋 **正式环境**：有真实用户之后，拆分为 `production` 分支 + 第二个 Render 服务 + Neon 数据库分支。
- 📋 **数据库迁移工具（Alembic）**：等需要修改已有的表时再引入。
- 📋 Render 和 Neon 放到同一个区域，降低数据库延迟（Render 服务的区域在创建后不能更改，需要新建服务）。
